# 🧩 Кейс: «Тариф, который ломал систему»

## 🎭 Контекст истории

Компания **«TaskFlow»** развивает продукт управления задачами.

Ключевой сервис — `profile-service`.  
Он определяет **тариф пользователя** (`base` / `max`) на основе количества задач, получаемого из сервиса `analytic-service`.

```go
	// если задач [0,5] -> base
	switch {
	case taskCount >= 0 && taskCount <= 5:
		p.Tariff = value_object.TariffBase
	case taskCount > 5:
		p.Tariff = value_object.TariffMax
	default:
		p.Tariff = value_object.TariffUnknown
	}
```

> ⚠️ **Ручка профиля очень критична для бизнеса**  
> Она используется:
> - при создании задач
> - при отображении лимитов
> - при биллинге

> ⚠️ Для бизнеса важнее отдать пользователю тариф, чем отказать в ответе.
> Если корректно определить тариф невозможно, допустимо временно вернуть базовый тариф.

**SLO** для ответа `profile-service` — **не более 300ms**.
---

## 🧱 Архитектура

client → api-gateway → profile-service → analytic-service

Взаимодействие по **gRPC**:
- `analytic-service` — нестабильный, не оптимизированные сервис
- `profile-service` — стабильный, бизнес-критичный

---

## ⚠️ Проблема

В процессе нагрузочного тестирования выяснилось:

- `analytic-service` **иногда работает медленно**
- иногда отдаёт **редкие ошибки**
- иногда “флапает” (успех / ошибка вперемешку)

При этом:
- профиль начинает отвечать **долго**
- иногда отдаёт **ошибки пользователям**
- нагрузка на систему растёт каскадно

Тимлид формулирует задачу:

> «Profile **не имеет права** быть медленным или часто падать,  
> даже если analytic ведёт себя плохо»

## 🧪 Режимы работы `analytic-service`

Для исследований и отладки в `analytic-service` реализована ручка управления режимами работы.

```go
const (
	OK        Mode = "ok"
	Error     Mode = "error"
	RareError Mode = "rare_error"
	Slow      Mode = "slow"
	Flaky     Mode = "flaky"
)

OK — отвечает быстро и стабильно

Error — всегда возвращает ошибку

RareError — редко (с вероятностью 5%) может вернуть ошибку

Slow — отвечает с растущей задержкой (без ограничений для простоты)

Flaky — ошибки и успехи чередуются с вероятностью 40%
```

Управление режимами осуществляется путем вызова http обработчика с переданным режимом. Изначально сервис стабилен и находится в режиме `OK`

- Перевод в `error` -> `curl "http://localhost:8084/mode?mode=error"`   
- Перевод в `rare_error` -> `curl "http://localhost:8084/mode?mode=rare_error"`   
- Перевод в `slow` -> `curl "http://localhost:8084/mode?mode=slow"`  
- Перевод в `flaky` -> `curl "http://localhost:8084/mode?mode=flaky"`   
- Перевод в `ok` -> `curl "http://localhost:8084/mode?mode=ok"`

В ответ на вызов будет что-то такое: `mode set to slow`

## 🔁 Генератор нагрузки (Load Generator)

Для исследования поведения системы используется **скрипт генерации нагрузки**,  
который регулярно вызывает ручку `profile-service` и логирует результаты.

Он расположен в директории `cmd/generator` в сервисе `profile-service`


Цель генератора — **создать стабильный, предсказуемый поток запросов**,  
на фоне которого можно наблюдать:
- рост latency
- появление ошибок
- срабатывание timeout
- открытие и закрытие circuit breaker
- работу graceful degradation
---

### 📌 Назначение

Генератор нагрузки предназначен для:

- постоянного создания трафика в систему
- имитации реальных пользовательских запросов
- наблюдения эффектов деградации зависимых сервисов
- экспериментов с конфигурацией timeout / retry / circuit breaker

---

### ⚙️ Принцип работы

- Генератор выполняет **gRPC-запросы в `profile-service`**
- Запросы отправляются **с фиксированным интервалом** (~500ms)
- Используются **разные `user_id`**:

### Задача 3 — Защита от нестабильного сервиса
> Analytic может быть нестабилен некоторое время.
Его нужно изолировать, чтобы при проблемах он смог восстановиться и не влиял на клиентов

1. Исследование
   - изучите поведение сервиса `analytic` при переходе из:
        - `ok → error`
        - `ok → slow`
        - `slow → ok`
        - `error → ok`
   - проанализируйте время и логи в моменты переключения режимов. Это вам поможет в дальнейшем

2. Внедрите защитный механизм, который:
    - ограничивает поток запросов к analytic при его нестабильной работе
    - позволяет системе разгружать зависимый сервис
    - поддерживает контролируемое восстановление (восстановиться можно, переключив режим в `ok`, скажем, после `slow|error`)

3. Анализ проделанного:
    - после внедрения механизма проанализируйте, как ведет себя система сейчас при обнаружении нестабильности `analytic-service`
    - изучите все фазы (`CLOSED` -> `OPEN` -> `HALF-OPEN` -> `CLOSED\OPEN`)

Например:
- после режима `error` можно в логах сервиса `profile-service` увидеть попытки восстановления
- если сервис `analytic` все так же сыпет ошибками, то восстановления не будет. И в обратную сторону, если ошибок нет и мы переведем в режим `ok`, то это будет сигналом о том, что работа восстановлена

Ожидание:
- при серьёзных проблемах analytic перестаёт получать основной трафик
- запросы в profile-service fail-fast
- восстановление происходит через HALF-OPEN / проверки
