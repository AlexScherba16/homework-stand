# 🧩 Кейс: «Тариф, который зависел от аналитики»

## 🎭 Контекст истории

Компания **«ТаскТрек»** развивает систему управления задачами.  
У пользователей есть тарифы, которые зависят от количества созданных ими задач:

- `< 5 задач` → **base**
- `> 10 задач` → **max**

Определением тарифа занимается `profile-service`.

Он определяет **тариф пользователя** (`base` / `max`) на основе количества задач, получаемого из сервиса `analytic-service`.

```go
	// если задач [0,5] -> base
	switch {
	case taskCount >= 0 && taskCount <= 5:
		p.Tariff = value_object.TariffBase
	case taskCount > 5:
		p.Tariff = value_object.TariffMax
	default:
		p.Tariff = value_object.TariffUnknown
	}
```

Чтобы понять, сколько у пользователя задач, `profile-service` синхронно ходит в  
`analytic-service` по gRPC: profile → analytic → возвращает кол-во задач → profile считает тариф


Именно здесь и начинаются проблемы.

---

## 🚨 Что случилось в проде

В определённый момент `analytic-service` начал вести себя нестабильно:

- стал отвечать периодами ошибками
- иногда начинал резко тормозить
- иногда «флапал» — то работает, то нет
- под нагрузкой начинал отвечать всё медленнее и медленнее

Это сказывалось на критически важном сервисе профиля для компании.

Пользователи начали получать:

- ошибки при запросе профиля
- долгие ответы
- таймауты
- нестабильность API

Хотя по факту **профиль сам по себе полностью рабочий**.  
Он просто зависел от нестабильной аналитики.

---

## ⚠️ Бизнес-аксиома

> **Отсутствие тарифа хуже, чем неточный тариф.**

Если корректно посчитать тариф невозможно, допустимо временно вернуть  
**базовый тариф**, но **недопустимо** отдавать ошибку пользователю.

Система должна **деградировать**, а не **отказывать**.

## 🧠 Что нужно понять инженеру

В этой истории есть три разные проблемы:

1. `profile-service` напрямую зависит от стабильности `analytic-service`
2. `profile-service` своими запросами может «добить» умирающий `analytic-service`
3. Даже когда аналитика тормозит, профиль продолжает её ждать и нарушает свой SLO

Вам предстоит решить все три.

## 🎯 SLO профиля

Ручка получения тарифа у `profile-service`:

- **SLO по времени ответа ≤ 300ms**
- **Практически не должна возвращать ошибки**
- В случае проблем с `analytic-service` должна стремиться к отсутствию ошибок

## 🎭 Режимы работы `analytic-service`

Для исследования проблемы у вас есть возможность переключать режим работы аналитики:

```go
const (
	OK        Mode = "ok"
	Error     Mode = "error"
	RareError Mode = "rare_error"
	Slow      Mode = "slow"
	Flaky     Mode = "flaky"
)
```

- `ok` — отвечает быстро и стабильно

- `error` — всегда возвращает ошибку

- `rare_error` — редко (с вероятностью 5%) может вернуть ошибку

- `slow` — отвечает с растущей задержкой (без ограничений для простоты)

- `flaky` — ошибки и успехи чередуются с вероятностью 40%

Управление режимами осуществляется путем вызова http обработчика с переданным режимом. Изначально сервис стабилен и находится в режиме `ok`.

Переключение выполняется так (передать надо нужный режим в виде строки):
> ` curl "http://localhost:8084/mode?mode=ok|error|rare_error|slow|flaky"`

В ответ на вызов будет это: `mode set to <mode>`.

Перед выполнением задания советую все же понять, как работает сервис в разных режимах.

Для теста можно подергать ручку сервиса аналитики напрямую через:

1) grpcui командой `grpcui --plaintext localhost:7004`
2) вызвать ее в `swagger` по адресу `http://localhost:8084/docs`

## 🔁 Генератор нагрузки (Load Generator)

Для исследования поведения системы используется **скрипт генерации нагрузки**,  
который регулярно вызывает ручку `profile-service` и логирует результаты (вызывает каждые 500ms).

Он расположен в директории `cmd/generator` в сервисе `profile-service` и является простым исполняемым файлом.

Цель генератора — **создать стабильный, предсказуемый поток запросов**,  
на фоне которого можно наблюдать:
- рост latency
- появление ошибок
- срабатывание timeout
- открытие и закрытие circuit breaker
- работу graceful degradation

### 📌 Назначение

Генератор нагрузки предназначен для:

- постоянного создания трафика в систему
- имитации реальных пользовательских запросов
- наблюдения эффектов деградации зависимых сервисов
- экспериментов с конфигурацией timeout / retry / circuit breaker

### ⚙️ Принцип работы

- Генератор выполняет **gRPC-запросы в `profile-service`**
- Запросы отправляются **с фиксированным интервалом** (~500ms)
- Используются **разные `user_id`**
- Запросы имеют установленный `timeout = 3s` (это нам еще пригодится)

В реализации gobreaker (https://github.com/sony/gobreaker) можно найти такой сниппет:

```go
func (cb *CircuitBreaker[T]) onSuccess(state State, age uint64, now time.Time) {
    switch state {
        case StateClosed:
            cb.counts.onSuccess(age)
        case StateHalfOpen:
            cb.counts.onSuccess(age)
            if cb.counts.ConsecutiveSuccesses >= cb.maxRequests {
                cb.setState(StateClosed, now)
            }
        }
}
```

### 🔹Задание 3 - Защита аналитики

Представьте ситуацию:

`analytic-service` начинает работать нестабильно.  
Он отвечает с ошибками, тормозит или работает «рывками».

При этом `profile-service` продолжает отправлять в него запросы с прежней интенсивностью,  
так как для него ничего «не изменилось».

В результате вы наблюдаете:

- рост количества запросов в сторону аналитики
- аналитика начинает «захлёбываться» ещё сильнее
- профиль получает всё больше ошибок и задержек
- система входит в спираль деградации

### Ваша задача

Реализовать механизм в `profile-service`, который:

- позволит **распознать**, что зависимый сервис работает нестабильно
- временно **прекратит** активные запросы в его сторону
- будет **периодически проверять**, восстановился ли он
- автоматически вернётся к обычной работе после восстановления

Все указывает на 1 **конкретный** подход, который был рассмотрен во втором уроке :)

### Проверьте своё решение:

Проверка заключается в том, что мы на работающем стенде запускаем генератор нагрузки, который ходит в сервис профиля.

Однако для демонстрации сбоя мы имеем право переключать режимы работы сервиса аналитики.

Например:
- Хочу после запуска заставить его вести себя нестабильно
   - перевожу из `ok` -> `flaky` (периодически с 40% вероятностью отдаю ошибки)
   - перевожу из `ok` -> `error` (делаю постоянный error rate)
   - перевожу из `ok` -> `slow` (делаю нарастающую задержку каждый запрос)
- Хочу из нестабильного режима стабилизировать систему
   - перевожу из любого негативного режима в `ok` (да, пусть это происходит моментально, что почти никогда не происходит в реальных системах)

Во время нахождения в каждом режиме стоит тщательно изучить логи генератора нагрузки:
- успех/неуспех
- само тело ответа
- время выполнения запроса
- момент времени получения ответа

Так же для анализа работы вашего решения необходимо изучить логи сервиса `profile-service`, т.к. он является клиентом к нестабильному сервису и мы внедряем защиту именно туда
- нам интересно видеть все переходы (тут спойлер уже, хех) по статусам нашего решения
- время переходов
- условия переходов (как мы поняли, что сервис помер и ходить в него не надо?)

Анализ логов обеих сторон вам даст полную картину жизненного цикла внедренной защиты в неблагоприятных условиях.

Я так же настоятельно рекомендую покопаться в коде, который расположен в соответствующей папке в директории `/pkg`.
